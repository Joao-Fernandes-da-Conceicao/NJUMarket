### 2. 核心技术方案

#### 2.1 页面静态化 + CDN

**目的**：减少服务器压力，提高响应速度

**实现方式**：
1. **提前生成静态页面**：秒杀开始前，将商品详情页生成静态 HTML
2. **CDN 分发**：将静态页面分发到 CDN 节点
3. **用户访问**：用户直接从 CDN 获取页面，不经过后端服务器

**优势**：
- ✅ **减少服务器压力**：90%+ 的请求在 CDN 层被处理
- ✅ **提高响应速度**：CDN 节点距离用户更近，延迟更低
- ✅ **降低成本**：减少服务器带宽和计算资源

**示例**：
```
秒杀商品页面：https://seckill.example.com/item/12345.html
→ CDN 节点：北京、上海、广州、深圳...
→ 用户从最近的 CDN 节点获取页面
```

#### 2.2 流量拦截与限流

**多层限流策略**：

**第1层：前端限流**
```javascript
// 前端令牌桶限流
class TokenBucket {
    constructor(capacity, refillRate) {
        this.capacity = capacity;      // 桶容量
        this.tokens = capacity;        // 当前令牌数
        this.refillRate = refillRate;  // 每秒补充令牌数
        this.lastRefill = Date.now();
    }
    
    consume() {
        this.refill();
        if (this.tokens > 0) {
            this.tokens--;
            return true;
        }
        return false;  // 限流
    }
}
```

**第2层：网关限流（Nginx）**
```nginx
# Nginx 限流配置
limit_req_zone $binary_remote_addr zone=seckill:10m rate=10r/s;

location /seckill {
    limit_req zone=seckill burst=20 nodelay;
    proxy_pass http://backend;
}
```

**第3层：应用层限流**
```java
// 令牌桶限流（Guava RateLimiter）
RateLimiter rateLimiter = RateLimiter.create(1000); // 每秒1000个请求

if (!rateLimiter.tryAcquire()) {
    return Result.fail("系统繁忙，请稍后重试");
}
```

**限流维度**：
- ✅ **IP 限流**：防止单个 IP 恶意请求
- ✅ **用户限流**：防止单个用户刷接口
- ✅ **商品限流**：防止单个商品被过度请求
- ✅ **全局限流**：保护系统整体稳定性

#### 2.3 库存预热

**目的**：将库存数据提前加载到 Redis，减少数据库压力

**实现方式**：
```java
// 秒杀开始前，将库存加载到 Redis
@Scheduled(cron = "0 0 0 * * ?")  // 每天凌晨执行
public void preloadStock() {
    List<SeckillItem> items = seckillItemService.getTodaySeckillItems();
    for (SeckillItem item : items) {
        // 将库存加载到 Redis
        redisTemplate.opsForValue().set(
            "seckill:stock:" + item.getId(),
            item.getStock()
        );
    }
}
```

**优势**：
- ✅ **减少数据库压力**：库存查询直接从 Redis 获取
- ✅ **提高响应速度**：Redis 查询延迟 < 1ms
- ✅ **支持高并发**：Redis 单机可支持 10万+ QPS

#### 2.4 异步下单（消息队列）

**架构设计**：

```
用户请求
    ↓
Lua 脚本（原子性）
    ├─ 扣库存（Redis）
    ├─ 记录用户（Redis Set）
    └─ 发送消息（MQ）
    ↓
返回成功（立即返回）
    ↓
消息队列（异步处理）
    ↓
消费者（写入数据库）
```

**Lua 脚本**：
```lua
-- 1. 判断库存
if tonumber(redis.call('get', stockKey)) <= 0 then
    return 1  -- 库存不足
end

-- 2. 判断重复下单
if redis.call('sismember', orderKey, userId) == 1 then
    return 2  -- 重复下单
end

-- 3. 扣库存
redis.call('incrby', stockKey, -1)

-- 4. 记录用户
redis.call('sadd', orderKey, userId)

-- 5. 发送消息到 MQ
redis.call('xadd', 'stream.orders', '*', 'userId', userId, 'itemId', itemId, 'orderId', orderId)

return 0  -- 成功
```

**消息队列选择**：
- **RocketMQ**：阿里开源，适合电商场景，支持事务消息
- **Kafka**：高吞吐量，适合大规模场景
- **Redis Stream**：轻量级，适合中小规模场景

#### 2.5 数据库优化

**分库分表**：
```sql
-- 订单表按用户ID分表
CREATE TABLE order_0 (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,

**读写分离**：
- **主库**：处理写操作（创建订单）
- **从库**：处理读操作（查询订单）

**连接池优化**：

```

## 🚄 12306 系统架构分析

### 3. 12306 系统特点

#### 3.1 业务特点

**高并发场景**：
- **春运期间**：单日访问量 > 1亿次
- **抢票高峰**：瞬时 QPS > 100万
- **数据量**：车次、座位、订单数据量巨大

**业务复杂度**：
- **座位分配**：需要考虑座位类型、车厢、座位号
- **余票计算**：实时计算各站点的余票
- **订单处理**：需要处理支付、退票、改签等

#### 3.2 技术架构

**分层架构**：

```
┌─────────────────────────────────────────┐
│  前端层                                  │
│  - 静态资源 CDN                          │
│  - 页面缓存                              │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  网关层                                  │
│  - 流量控制                              │
│  - 请求过滤                              │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  应用层                                  │
│  - 余票查询服务（多实例）                │
│  - 下单服务（多实例）                    │
│  - 支付服务                              │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  缓存层                                  │
│  - Redis（余票缓存）                     │
│  - 分布式缓存                            │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  数据层                                  │
│  - MySQL（主从复制）                     │
│  - 分库分表                              │
│  - 读写分离                              │
└─────────────────────────────────────────┘
```

#### 3.3 核心技术

**1. 余票计算优化**

**问题**：实时计算各站点的余票非常复杂

**解决方案**：
- ✅ **预计算**：提前计算好各站点的余票
- ✅ **Redis 缓存**：将余票数据缓存到 Redis
- ✅ **增量更新**：每次下单后，增量更新余票

**2. 座位分配算法**

**问题**：如何高效分配座位，避免冲突

**解决方案**：
- ✅ **分段锁**：按车厢分段加锁
- ✅ **预分配**：提前分配座位号
- ✅ **冲突检测**：使用 Redis Set 记录已分配座位

**3. 订单处理**

**问题**：高并发下单，如何保证数据一致性

**解决方案**：
- ✅ **分布式锁**：使用 Redis 分布式锁
- ✅ **数据库事务**：使用数据库事务保证一致性
- ✅ **消息队列**：异步处理订单，提高响应速度

## 🎯 技术选型建议

### 6. 不同规模的技术选型

#### 6.1 小规模项目（< 1万 QPS）

**推荐技术栈**：
- ✅ **Redis Stream + Lua 脚本**：简单高效
- ✅ **单库单表**：数据量小，不需要分库分表
- ✅ **应用层限流**：Guava RateLimiter
- ✅ **同步下单**：直接操作数据库

**参考项目**：hm-dianping（学习项目）

#### 6.2 中规模项目（1-10万 QPS）

**推荐技术栈**：
- ✅ **RocketMQ**：支持事务消息
- ✅ **Redis 缓存**：库存预热
- ✅ **读写分离**：主从复制
- ✅ **多层限流**：网关 + 应用层

**参考项目**：中小型电商平台

#### 6.3 大规模项目（> 10万 QPS）

**推荐技术栈**：
- ✅ **页面静态化 + CDN**：减少服务器压力
- ✅ **Kafka**：高吞吐量消息队列
- ✅ **分库分表**：水平扩展
- ✅ **多层限流**：前端 + 网关 + 应用层
- ✅ **监控告警**：完善的监控系统

**参考项目**：12306、淘宝、京东

## 📝 总结

### 7. 核心结论

#### 7.1 大规模秒杀系统的关键点

1. **流量控制**：多层限流，防止系统崩溃
2. **页面优化**：静态化 + CDN，减少服务器压力
3. **库存预热**：提前加载到 Redis，提高响应速度
4. **异步处理**：消息队列削峰，提高系统吞吐量
5. **数据优化**：分库分表、读写分离，提高数据库性能

#### 7.2 学习项目的价值

**学习价值**：
- ✅ **理解核心原理**：Lua 脚本原子性、消息队列削峰
- ✅ **掌握基础技术**：Redis、MQ、分布式锁
- ✅ **学习架构设计**：分层架构、异步处理

**局限性**：
- ⚠️ **无法模拟真实场景**：缺少高并发、大数据量
- ⚠️ **基础设施不足**：缺少 CDN、负载均衡等
- ⚠️ **运维能力有限**：缺少监控、告警等

#### 7.3 如何向大规模项目看齐

**技术层面**：
1. **引入 CDN**：使用阿里云 CDN、腾讯云 CDN
2. **完善限流**：实现多层限流策略
3. **优化数据库**：考虑分库分表、读写分离
4. **完善监控**：引入 Prometheus + Grafana

**架构层面**：
1. **微服务化**：将系统拆分为多个微服务
2. **容器化**：使用 Docker + Kubernetes
3. **自动化**：CI/CD 自动化部署
4. **高可用**：多机房部署、容灾备份
