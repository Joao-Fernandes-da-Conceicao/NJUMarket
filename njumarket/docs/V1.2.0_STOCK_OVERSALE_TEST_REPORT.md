# 📊 库存超卖防护测试报告 v1.2.0

## 📋 测试概述

### 测试版本
**v1.2.0** - 库存超卖防护功能

### 测试目标
验证系统在高并发场景下是否能正确防止**库存超卖**问题，确保库存数据的准确性和一致性。

### 测试场景
- **并发用户数**：100个用户
- **测试商品库存**：10
- **每个用户购买数量**：1
- **预期结果**：只有10个订单成功，90个返回"库存不足"

---

## 🎯 并发量评估

### 项目规模分析

**项目特征**：
- 校园二手交易平台
- 用户规模：10万以下
- 商品特征：大部分商品库存为1（二手商品）
- 业务场景：典型的P2P交易模式

### 并发量合理性评估

| 评估维度 | 实际情况 | 评估结果 |
|---------|---------|---------|
| **用户规模** | 10万用户 | ✅ 合理 |
| **并发用户数** | 100个并发 | ✅ 贴合 |
| **启动时间** | 5秒内启动 | ✅ 合理 |
| **测试库存** | 10个库存 | ✅ 贴合实际（热门商品） |
| **并发比例** | 0.1%用户同时下单 | ✅ 符合校园场景 |

### 结论

✅ **并发量贴合项目实际情况**

**理由**：
1. **校园场景特点**：
   - 单个热门商品可能有50-200人同时关注
   - 实际同时下单的并发量通常在10-100之间
   - 100并发用户测试能覆盖大部分真实场景

2. **库存特征**：
   - 大部分商品库存为1（二手商品）
   - 测试使用库存10，代表热门商品场景
   - 100并发用户抢10个库存，能有效验证超卖防护

3. **压力测试**：
   - 100并发用户已能充分验证系统并发处理能力
   - 对于10万用户规模的平台，100并发是合理的测试压力

## 🧪 测试配置

### 测试环境

- **后端服务**：`http://localhost:8080`
- **数据库**：MySQL
- **缓存**：Redis（用于分布式锁）
- **测试工具**：Apache JMeter 5.6.3

### JMeter测试配置

| 配置项 | 值 | 说明 |
|--------|---|------|
| **线程数（并发用户）** | 100 | 100个用户同时下单 |
| **启动时间（Ramp-up）** | 5秒 | 5秒内启动所有线程 |
| **循环次数** | 1 | 每个用户只执行一次 |
| **测试商品ID** | `COMMODITY_1762336718431_528` | 测试商品 |
| **测试商品库存** | 10 | 初始库存为10 |
| **每个用户购买数量** | 1 | 每个用户购买1件 |

### 测试数据

**CSV数据文件**：`user_tokens.csv`
- 包含100个测试用户的token
- 格式：`username,phone,token,userId`
- 已配置忽略第一行表头

**请求配置**：
- **接口路径**：`POST /api/user/order/create`
- **请求头**：
  - `Content-Type: application/json`
  - `Authorization: Bearer ${token}`
- **请求体**：
  ```json

    "commodityId": "COMMODITY_1762336718431_528",
    "quantity": 1,
    "payAmount": 114.00,

    "remark": "JMeter压力测试"
  }
  ```


```sql

-- 结果：0 ✅
```

**验证**：✅ 库存准确扣减，无负数，无超卖

#### 2. 订单数量验证

```sql

WHERE commodity_id = 'COMMODITY_1762336718431_528'
```

**验证**：✅ 订单数等于库存，无超卖

## 🛡️ 防护机制验证

### 三重保护机制验证

#### 1. Redis分布式锁 ✅

**验证**：
- 多服务器场景下的并发控制
- 防止不同服务器同时处理同一商品订单
- 锁的获取和释放正常

**日志验证**：
- 无"获取分布式锁失败"的警告
- 锁正常释放

#### 2. 数据库悲观锁 ✅

**验证**：
- 使用 `SELECT ... FOR UPDATE` 锁定商品行
- 防止同一服务器内多个事务并发修改
- 事务隔离正常

#### 3. 数据库条件更新 ✅

**验证**：
- 使用 `UPDATE ... WHERE stock >= quantity` 条件更新
- 数据库层面的最终保护
- 即使前两层保护失效，也能防止超卖
